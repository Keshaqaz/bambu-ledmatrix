# Session Context: 2026-06-15

## Итог

Матрица работает на прошивке `4.0.10-2026.06.15`, слот `app1`.

За сессию закрыты три симптома:

1. Исчезновение полосы прогресса Bambu исправлено в исходниках и уже было
   загружено в устройство как `4.0.1`.
2. Отдельная неисправность отображения температуры не подтвердилась. WebUI ранее
   показывал актуальные `+17.2°C` из Open-Meteo, пользователь подтвердил, что
   матрица сейчас работает, а локальная проверка рендера не выявила выхода
   пикселей температуры за границы экрана.
3. Перегрев ESP32-C3 после последних изменений устранён в `4.0.5`. На `4.0.4`
   внутренний датчик показывал `71.3 °C` после 22 минут работы. После перехода
   на адаптивное обновление экрана `4.0.5` показала `49.3 °C` через 4 минуты и
   `51.3 °C` через 5 минут.

Финальная прошивка `4.0.5` была загружена через HTTP OTA `/api/update`;
устройство подтвердило версию и переход слота `app1 → app0` через `/api/status`.
После следующей перезагрузки температура не загрузилась, поэтому проведена
дополнительная диагностика погодного транспорта. Финальная прошивка `4.0.10`
идёт HTTP-first с последовательным HTTPS-фоллбэком, временно выключает Wi-Fi
power save на время `fetchWeather()` и показывает gateway/DNS/resolved IP в
`/api/status`. `/api/status` подтвердил `4.0.10-2026.06.15`, слот `app1`, и
успешную погоду OWM `200`: `17.19 °C`.

## Исправление перегрева

В `4.0.4` основной `loop()` проверял возможность рендера с частотой 50 Гц, а
`showClockTemp()` вызывался каждые 250 мс независимо от того, был ли экран
статичным. Кэш предотвращал лишний `FastLED.show()`, но CPU всё равно слишком
часто просыпался и пересчитывал ключ кадра.

В `4.0.5`:

- статичный экран проверяется раз в секунду;
- `FastLED.show()` выполняется только при изменении минуты, температуры,
  настроек, Wi-Fi-индикатора или состояния Bambu;
- 250 мс / 4 FPS остаются только для анимированных состояний `preparing`,
  `paused`, `finished`, `error`;
- основной цикл обслуживает WebServer и ArduinoOTA с частотой 20 Гц и делает
  `delay(50)` между проходами.

Контрольные значения `/api/status`:

```text

4.0.5, app0, uptime 0ч 4м:  cpuTemp 49.3°C
4.0.5, app0, uptime 0ч 5м:  cpuTemp 51.3°C
```

## Исправление прогресса Bambu

Причина исчезновения полосы была в прошивке ESP32: один неудачный запрос к
relay, краткая потеря Wi-Fi или временный статус `unknown/offline` сразу
очищали `displayLifecycle` и `progress`.

В `esp32_matrix_controller22/src/app.cpp` теперь:

- последний видимый оверлей (`preparing`, `printing`, `paused`, `finished`,
  `error`) сохраняется при временном `unknown/offline`, ошибке HTTP и потере
  Wi-Fi;
- прогресс сохраняется вместе с оверлеем;
- оверлей очищается по явному `idle`, при отключении Bambu или удалении
  настройки relay.

Исправление прогресса сохранено в текущих исходниках и входит в установленную
версию `4.0.5-2026.06.15`.

## Погодный транспорт 4.0.10

После перезагрузки на `4.0.5` температура была `-999`, а диагностика показывала
ошибки соединения погодных API. Первичная гипотеза, что фоллбэки не запускаются,
не подтвердилась: опрос `/api/status` во времени показал переходы через OWM HTTP,
OWM HTTPS, Open-Meteo HTTP и Open-Meteo HTTPS. Проблема была в промежуточных TCP
отказах до HTTP-ответа, а не в остановке control flow.

В `4.0.10` текущий порядок и диагностика такие:

- OWM: HTTP, затем HTTPS;
- Open-Meteo: HTTP, затем HTTPS;
- HTTP и HTTPS клиенты создаются строго последовательно, не одновременно, чтобы
  не повторить переполнение 20 KB стека `weatherTask` из эксперимента `4.0.2`;
- на время `fetchWeather()` вызывается `esp_wifi_set_ps(WIFI_PS_NONE)`, на выходе
  возвращается `WIFI_PS_MIN_MODEM`;
- `/api/status` отдаёт `gateway`, `subnet`, `dns0`, `dns1`; `weatherError`
  включает resolved IP и gateway при ошибках;
- известный компромисс: OWM API key при HTTP передаётся открытым текстом.

Проверка после OTA:

```text

Sketch uses 1351929 bytes (68%)
Global variables use 46596 bytes (14%)
gateway: 192.168.1.1
dns0: 192.168.1.1
weatherCode: 200
weatherSource: owm

```

Диагностическая `4.0.7` показала, что DHCP/маршрут/DNS корректны:
`gateway=192.168.1.1`, `dns0=192.168.1.1`, OWM резолвился в `176.9.63.49`.
Диагностическая `4.0.9` с raw TCP probe подтвердила, что ранние отказы происходят
до HTTPClient (`tcp=fail`), но следующий шаг/повтор фоллбэка получил OWM `200`.
Raw probe удалён из production-кода; в финальной `4.0.10` оставлены только
полезные diagnostics и Wi-Fi power-save guard. После OTA `4.0.10` автоматический
и ручной refresh вернули OWM `200` и `17.19 °C`.

## Решение по эксперименту 4.0.3

Незагруженный эксперимент `4.0.3` с переводом OWM на обычный HTTP удалён из
рабочего дерева.

Причины:

- он не решал задачу физического отображения температуры;
- рабочая `4.0.1` уже получила температуру через Open-Meteo;
- обычный HTTP раскрывал бы OWM API key в сети;
- исходники должны соответствовать реально установленной рабочей версии.

В `4.0.10` plain HTTP возвращён как первая последовательная попытка для OWM и
Open-Meteo, а HTTPS оставлен фоллбэком. Одновременный HTTPS→HTTP fallback с
двумя клиентами не возвращать: эксперимент `4.0.2` переполнил 20 KB стек
`weatherTask` и вызвал boot loop.
